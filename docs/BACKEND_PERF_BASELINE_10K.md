## 4. DB-4 改写与前后对比（2026-11-23）

证据链：SQL 全部 ≤20ms 而端点 686ms p50 ⇒ 成本在 Node 侧。定位到 `listItemsPaged` 两处：
① `item_content` **全表**拉进内存建 Map（每请求多 MB）；② `q` 过滤在分页后的 JS 里做（只能
命中一页内的行，`total` 也是错的）。改写：内容只取页内行（inArray 页 id）+ `q` 下推 SQL
（title/source_label/content_text EXISTS 子查询，D-020 口径）。

| 工作负载 | p50 改写前→后 (ms) | p95 改写前→后 (ms) |
|---|---|---|
| list items (page 200) | 686.4 → 166.6（-76%） | 867.0 → 189.6（-78%）✅ 回到读 p95 500ms SLO 内 |
| list items (keyword filter) | 683.8 → 256.5（-62%） | 879.2 → 269.6（-69%）✅ |
| item detail | 31.1 → 33.7 | 47.0 → 54.2 |
| create item | 33.0 → 42.9 | 35.9 → 57.4 |
| list contexts | 34.5 → 42.1 | 39.1 → 63.6 |
| search（代码未动） | 496.1 → 649.1 | 549.3 → 751.9 |
| relations projection | 19.7 → 22.8 | 22.7 → 27.1 |

注记：① 非热点负载的 ±10ms 波动是机器负载噪声（同机有并行任务在跑），detail/create/contexts/
relations 代码未动、无趋势性变化；② `search` 端点（`repo/search.ts` 的 itemTextForFilter 全表
扫描）本次未改，p95 752ms 超 SLO——已列 DB-4 后续候选（与 P3 语义检索 GAP-14 一并裁）；
③ 改写回归由 176 个既有测试覆盖（q 语义测试全绿）。
